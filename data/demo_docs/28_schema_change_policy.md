# AtlasDesk v2 Schema 变更策略

**变更原则**
本文是虚构演示资料，讨论同一系统的数据结构演进，不新增一个未说明的产品版本。每次结构变更独立记录目标、兼容范围、迁移步骤、数据回填及回退条件。程序可以重新启动并不表示旧程序能理解新结构，也不表示业务数据可以无损恢复。

**兼容执行**
优先使用先扩展再收缩的步骤：先增加兼容结构，使新旧程序在观察窗口内均能工作，再回填并校验数据，最后移除旧字段或旧路径。删除字段、改变含义和收紧约束前，检查 API、Worker、历史事件与人工运维脚本的读取方式，避免只测试创建接口而遗漏后台任务。

**迁移与回退**
从旧版升级时，执行顺序和起始版本仍以《迁移清单》为准。原文明确 ticket_events 迁移可逆，不代表所有将来的字段删除或数据改写都可逆。已经恢复新版业务写入后，禁止未经评估直接回迁或运行旧程序，必须执行《回滚手册》规定的数据导出、恢复和补偿决策。

**验证证据**
迁移验收同时检查记录数量、关键字段、租户边界、附件引用和待处理事件。回填任务使用可重复执行的进度记录，失败后从确认点继续，不通过重新执行全部副作用来碰运气。文档保存实际执行结果和失败样例，演示中的兼容性目标不能当作已经在生产验证的保证。
