# AtlasDesk v2 Worker 扩缩容与积压治理

## 扩缩容依据
本文是虚构演示资料，不包含真实吞吐量或扩容收益。Worker 与 API 独立调整数量，不能因为 API 流量升高就按同一比例复制 Worker。先检查待处理事件数量、最老事件等待时间、失败比例和下游响应，判断积压是处理能力不足还是外部接口故障造成。

## 扩容约束
增加 Worker 前核对数据库连接预算、Redis 协调能力、对象访问和回调接收方限流。数据库预留连接同时供 Worker、运维和监控使用，不是每个 Worker 都可以单独再领取二十个连接。外部消费者持续失败时盲目扩容可能增加重复请求和重试压力，不能解决错误地址或失效凭据。

## 缩容顺序
先停止目标进程领取新任务，再等待已经领取的任务完成。超过维护等待窗口时记录未确认事件，保留恢复信息后停止，不能直接删除事件让队列深度看起来归零。进程中断可能触发重新投递，因此消费者的 event_id 去重仍然必需，不能由扩缩容控制替代。

## 结果验证
调整后观察等待时间与错误比例是否改善，同时检查数据库连接等待和业务延迟是否恶化。记录副本数、事件类型和观察窗口，区分配置计算与实际测量。只有积压持续下降且接收方处理正常，才能认定本次调整有效；相关结论不能直接推广到其他租户或附件规模。
