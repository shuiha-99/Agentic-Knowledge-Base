# AtlasDesk v2 计划维护与业务恢复

## 维护准备
本文为虚构演示资料。维护前登记范围、预计影响、执行人、恢复负责人和终止条件，确认可恢复备份及相关配置快照。预先通知调用方暂停写入或降低请求量，但不能仅凭通知已经发送，就假定所有客户端都已停止提交业务。

## 停止顺序
涉及数据库变更时先关闭写入口，再让 Worker 停止领取并排空已经领取的任务。记录未确认通知与待处理事件，最后停止相关服务或执行维护。只清理缓存无法替代业务排空，直接删除 Redis 任务状态可能导致恢复后重复通知或漏掉人工核对步骤。

## 恢复顺序
先恢复 PostgreSQL 和 Redis，检查连接及目标版本，再启动 API。就绪探针正常后验证创建、查询与权限边界，随后启动 Worker 并观察积压。需要恢复数据库快照时，按《回滚手册》判断是否存在快照后的新写入，先保存补偿清单，不允许直接覆盖后再追查丢失内容。

## 结束标准
维护结束需要业务冒烟、通知核对、附件抽样和关键指标观察全部有记录。没有完整依据时保持受限入口并升级处理，不能为了赶维护窗口而将未完成项目标记为成功。旧版维护需要完整停机窗口；新版是否能够滚动处理，取决于本次变更和依赖兼容性，并非任何维护都可以无中断完成。
